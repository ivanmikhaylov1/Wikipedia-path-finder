# Переходы

Клиентский поиск цепочки гиперссылок между двумя статьями Википедии. React + TypeScript + Vite, двунаправленный BFS в Web Worker, запросы напрямую к MediaWiki Action API. Сервер не нужен.

Интерфейс «Несовместимые страницы»: две статьи на разорванном энциклопедическом
развороте, ограниченный поиск и лента результата в порядке переходов.
Prata — книжные заголовки, Oswald — контрастный набор, Golos Text — управление.
Единая бумажная палитра с ультрамарином. Поиск показывает реальные названия
проверяемых статей и счётчики из Worker; упорядоченный список результата сразу
содержит доступные ссылки на статьи. Декоративные движения конечны и отключаются
при reduced-motion.

## Локальный запуск

```bash
npm ci
npm run dev
```

Откройте адрес Vite из терминала. Для проверки: `npm test` и `npm run build`.

Введите название или URL вида `https://ru.wikipedia.org/wiki/Москва` в каждом поле.
Простое название ищется в русском разделе; URL задаёт язык статьи, а выбор
подсказки сохраняет её язык. Подсказки показывают разделы RU, EN, DE, FR и ES. У каждой
статьи видна метка языка; обмен полями сохраняет выбранные разделы. Если языки
отличаются, межъязыковой поиск включается автоматически. Пример начальной пары —
«Осьминоги» (RU) и «Bauhaus» (EN), без обещания найти связь.

Ссылки `?from=...&to=...&lang=...` заполняют форму; поиск запускается кнопкой
«Столкнуть», чтобы открытие ссылки не расходовало бюджет API. Межъязыковая ссылка
сохраняет URL обеих статей и `mode=multilingual`; старые ссылки с этим режимом
тоже читаются. «Поделиться» в результате копирует пару завершённого поиска.
«Новая пара» возвращает свежий пример и фокус в первое поле. Редиректы разрешаются
перед поиском. Новый поиск и кнопка остановки завершают старый Web Worker;
запоздавшие сообщения старого Worker игнорируются.

Иллюстрации осьминога и разрыва бумаги находятся в `public/images/collision/`,
зерно — в `public/images/grain.webp`. [Источники новых ассетов](docs/collision-assets.md).
Результат использует только настоящие названия и ссылки; описания и миниатюры
статей не загружаются. OG использует существующую гравюру осьминога. Иконки используют ту же бумажную, чёрную и ультрамариновую палитру.
`node scripts/prepare-icons.mjs` воспроизводит SVG и PNG-варианты.

## Как работает поиск

`src/lib/linkSource.ts` сохраняет обязательные операции `getOutlinks`, `getInlinks`, `resolveRedirect`; API-источник также предоставляет постраничное получение связей, канонизацию, проверку мостов и маршрутов. Поиск работает в одном Web Worker и использует общий источник, направленный граф обнаруженных связей, очередь и бюджет запросов.

В API-режиме три стратегии чередуются:

- Двунаправленный BFS систематически расширяет слои и получает ход в каждом активном раунде; до пяти статей одного слоя загружаются параллельно.
- Проверка мостов использует `prop=links` и `pltitles`, чтобы искать конкретные связи между уже исследованными областями, включая связи за пределами первой страницы API.
- Направленный поиск выбирает перспективные статьи по совпадениям слов в названии и связям с областью цели. Он может исследовать более глубокую ветку до завершения широкого слоя. Он получает ход раз в четыре раунда или при исчерпании обычного BFS. Это эвристика, а не гарантия успеха.

Реальная цепочка показывается сразу после проверки с надписью «Маршрут найден, ищем короче». Последующие результаты заменяют её только при меньшем числе переходов. Остановка, таймаут, исчерпание запросов или ошибка улучшения сохраняют найденный маршрут. «Искать короче» продолжает сохранённое состояние со свежим бюджетом, не скрывая результат. Новая пара или редактирование статей завершают старый Worker; запоздавшие сообщения игнорируются. Только появление первого результата может переводить фокус к заголовку; сокращение маршрута не забирает фокус у читателя.

API возвращает до 500 связей на страницу ответа, но новый источник может получать следующие страницы и сохраняет полный объект `continue` вместе с данными. На всю статью потолка 500 в новом API-поиске нет. Исходящие связи получает `generator=links` с `redirects=1`: API канонизирует цели в том же ответе без дополнительных запросов на каждые 50 названий; обратный поиск учитывает статьи, которые ссылаются на редиректы цели. Редирект не добавляет отдельный переход в цепочке. Проверка направлений не превращает входящую ссылку в исходящую.

Прогрессивные записи IndexedDB v4 отделены по языку, каноническому названию, направлению и параметрам запроса; данные хранятся 30 дней. Частичные списки и результаты точечных проверок не считаются полными списками соседей. Ранее загруженные рёбра проверяются заново перед публикацией маршрута; текущие ответы API уже служат доказательством. Кэш каждого посетителя остаётся на его устройстве и не передаётся другим посетителям. Недоступность IndexedDB не блокирует живой поиск. Старый API-адаптер и BFS остаются для совместимости и сравнения; их ограниченный обход не доказывает отсутствие связи.

Все запросы канонизации, пагинации, мостов, языковых переходов, проверки результата и повторы входят в общий бюджет. Транспорт сохраняет `Api-User-Agent`, Retry-After и экспоненциальные повторы 429/5xx. До пяти запросов поиска и один слот подсказок дают максимум шесть запросов приложения. Часть бюджета резервируется для проверки маршрута: непроверенную цепочку из старого кэша приложение не публикует при нехватке запросов.

| Лимит | Значение |
| --- | ---: |
| `maxDepth` | 6 шагов с каждой стороны BFS; направленная стратегия — до 12 шагов от начала |
| Длина публикуемого маршрута | не более 12 переходов |
| Страница выдачи связей API | до 500 результатов с возможностью продолжения |
| `maxTotalRequests` | 4000 HTTP-запросов на запуск или продолжение |
| `concurrency` | до 5 в Worker + 1 для подсказок |
| `requestTimeout` | 10 секунд, дополнительно ограничены оставшимся временем поиска |
| `searchTimeout` | 90 секунд на запуск или продолжение |
| `improvementTimeout` | до 8 секунд после первого результата, без продления при сокращении |
| `improvementMaxRequests` | до 80 дополнительных HTTP-запросов после первого результата |
| `retryAttempts` | 2 повтора при 429/5xx |

Найденный API-маршрут не обязательно глобально кратчайший. Отсутствие результата в пределах бюджета или глубины не доказывает отсутствие пути. API завершает улучшение раньше, если доказана оптимальность: найден прямой переход либо полностью раскрыты необходимые живые исходящие слои одного языка. Кэш, частичная пагинация и межъязыковой обход не дают такого доказательства. `exact` означает эту проверку или кратчайший путь в полном локальном графе. Локальный режим использует полный граф и прежний BFS без API-проверок.

### Сравнение алгоритмов

```bash
npm run benchmark:graph
npm run benchmark:search -- --runs 3
npm run benchmark:search -- --live --runs 1 --out docs/verification/anytime-live.json
```

Первый режим работает без сети: оба настоящих алгоритма проходят одинаковые HTTP-фикстуры с пагинацией, редиректами и фильтрами. Набор включает семь контрольных и восемь воспроизводимых случайных графов с циклами, алиасами и несвязными областями; холодный и прогретый кэши изолированы между алгоритмами. Прогрев получает соседей обоих концов в обоих направлениях в пределах возможностей каждого источника. Число запросов берётся из транспорта и исключает предварительный прогрев.

`--live` явно включает запросы к Wikipedia для четырёх пар: Cat → Animal, USA → North America, Fungus → Music и RU Осьминоги → EN Bauhaus, последовательно с паузами. Сравнение использует одинаковые ограничения: 100 запросов и 15 секунд на поиск. JSON содержит каждый запуск, успех, время и HTTP-запросы до первого проверенного маршрута, полное время, итоговую длину, число HTTP-запросов, стоимость каждой стратегии и причину завершения. Частичный прогрев указан отдельно; прогрев исключён из стоимости поиска. Node-прогон использует IPv4 и идентифицирующий User-Agent. Фикстуры проверяют алгоритм; их скорость не является измерением скорости Wikipedia в сети.

`benchmark:graph` отдельно сравнивает повторный обход и инкрементальные индексы на 120 тыс. и 1,1 млн рёбер; начальное построение индексов измеряется отдельно. [Результаты проверок и ограничения измерений](docs/api-anytime-search-report.md).

## Подключение локального графа

Скачайте дампы одного снимка и одного языка с https://dumps.wikimedia.org/: `page` и `pagelinks`, для современного формата также `linktarget`, для разрешения редиректов — `redirect`. Сборщик читает SQL или SQL.gz построчно, использует схему CREATE TABLE и делает два прохода по pagelinks, заполняя исходящую и входящую CSR без списка объектов на каждое ребро.

```bash
npm run build:graph -- --lang ru --page ruwiki-page.sql.gz --pagelinks ruwiki-pagelinks.sql.gz --linktarget ruwiki-linktarget.sql.gz --redirect ruwiki-redirect.sql.gz
VITE_LINK_SOURCE=local npm run build
npm run preview
```

Результат — `public/graphs/ru.bin.gz`; `--out` позволяет изменить путь. Старый pagelinks с `pl_namespace` и `pl_title` не требует linktarget. Без redirect редиректы остаются обычными узлами; для полноценного графа добавляйте этот дамп. Исключаются пространства имён кроме 0, красные ссылки и межвики-редиректы. Формат WPFG v1: заголовок little-endian, JSON названий/алиасов, две пары uint32-массивов offsets/targets, затем gzip. Исходящие рёбра редиректов исключены, цели ссылок разрешаются до канонических статей.

Локальный адаптер загружает граф статическим запросом один раз на язык в каждом воркере. Подсказки API отключены. Воркер использует все рёбра без потолка 500; BFS возвращает кратчайший путь в графе в пределах глубины и времени. Поиск не обращается к Wikipedia. Открытие карточки вручную ведёт на Wikipedia. Большие графы требуют памяти для названий, обоих CSR и распакованного файла; полный ruwiki/enwiki может не поместиться в мобильный браузер. Графы не входят в git и должны быть собраны до деплоя.

## Межъязыковой режим

В API-режиме выберите статьи из разных языковых разделов через подсказки или Wikipedia-ссылки: режим включится автоматически. Режим работает в разделах начальной и конечной статьи. Рёбра langlinks направленные: обратного индекса у Action API нет, поэтому адаптер использует прямой BFS и не выдумывает обратные переводы. Это медленнее двунаправленного поиска и ограничено шестью шагами от старта. Межъязыковой переход считается одним шагом; это переход языка, а не обязательно ссылка в тексте статьи. Локальный CSR пока одноязыковой.

## Проверки и PWA

```bash
npm test                     # включая 200 случайных графов, все пары и перебор
npm run build
npx playwright install chromium
npm run test:e2e             # замоканный Action API, axe, 360px, PWA офлайн
npm run test:local           # сборка тестового CSR, local build и реальный Worker
npm run measure:bundle       # <=30 КБ gzip относительно main, включая локальные шрифты
npm run test:lighthouse      # mobile аудит production-сборки
```

`test:local` создаёт тестовый `public/graphs/en.bin.gz` (шесть статей, это не дамп английской Wikipedia) и `dist-local/`. Удалите этот файл перед production-сборкой или замените полноценным графом. В CI тестовый файл удаляется автоматически. `npm run test:lighthouse` запускает preview при необходимости, использует установленный Playwright Chromium и сохраняет HTML/JSON в `lighthouse-reports/`; адрес можно переопределить `LIGHTHOUSE_URL`. `LIGHTHOUSE_URL` должен указывать на production-сборку. Проверки Playwright используют production preview и блокируют Service Worker в сценариях API, проверяя PWA отдельно. Артефакты: `playwright-report/`, `test-results/`.

CI (`.github/workflows/ci.yml`) проверяет pull requests и main: unit/property, сборку, E2E с axe, mobile Lighthouse, размер бандла и local Worker. Deploy workflow выполняет те же проверки перед публикацией и отдельно пересобирает приложение с GitHub Pages base. Для проверки по корню localhost поддерживается `VITE_BASE_PATH=/`.

Сборка генерирует manifest и версионный service worker: оболочка и локальные шрифты кэшируются при установке; небольшие декоративные изображения — по возможности. Большая гравюра кэшируется после запроса на широком экране. Сбой декоративного файла не блокирует установку. Wikipedia API офлайн недоступен; precache не сохраняет его ответы. IndexedDB-кэш ссылок остаётся отдельным. Графы не precache-ятся автоматически, чтобы установка PWA не скачивала гигабайты. В новом поиске новый Worker загружает локальный граф снова. Для установки PWA используйте HTTPS или localhost; manifest содержит SVG и PNG-иконки 192/512.

Dev-зависимости: Playwright — браузерные сценарии; `@axe-core/playwright` — доступность; Lighthouse — mobile аудит; `tsx` — выполнение типизированного сборщика. Новых runtime-зависимостей нет. `sharp` используется только для воспроизводимой подготовки ассетов. Prata, Oswald и Golos Text размещены локально с лицензиями SIL OFL в `src/assets/fonts/`.

## Деплой форка на GitHub Pages

1. Загрузите проект в репозиторий GitHub с веткой `main`.
2. В **Settings → Pages → Build and deployment** выберите **GitHub Actions**.
3. Push в `main` запускает тесты, сборку и публикацию `dist` через `.github/workflows/deploy.yml`.

При сборке в GitHub Actions `vite.config.ts` берёт имя репозитория из `GITHUB_REPOSITORY` и выставляет `base=/<repo>/`.

## Что означает найденный путь

Счётчик переходов и статей сообщает длину цепочки, а не гарантию оптимальности. Внутри одного раздела шаг — гиперссылка. В межъязыковом режиме шаг может вести к языковой версии статьи; список помечает смену языка (например, RU → EN), а соединитель рисуется пунктиром. Раздел — версия Википедии на языке (ru.wikipedia.org, en.wikipedia.org); раздел виден в метке у каждой статьи.

## Когда путь не найден

Это отдельное состояние `notFound`, а не начальное приглашение. Оно сохраняет число проверенных статей и достигнутую глубину, затем объясняет причину `limitsHit`: `depth` — предел глубины, `requests` — бюджет запросов, `time` — время, `no_path` — доступные связи исследованного графа проверены. Отсутствие пути в этом графе не доказывает его отсутствие во всей Википедии.

«Искать глубже» доступно только при сохранённом состоянии продолжения (`canResume`) и причине, отличной от `no_path`. Продолжение получает свежий бюджет запросов и времени, но не увеличивает предел глубины. BFS не сохраняет продолжение при `depth` и `no_path`; тогда доступны «Изменить статьи» (фокус на «Откуда») и «Поменять местами». При лимите без сохранённого состояния — те же действия, без совета увеличивать глубину.

Разворот показывает «Путь не найден» и действия восстановления; предварительный кандидат не подменяет это состояние. При reduced-motion итог показывается сразу. Ошибки пустого поля и неподдерживаемого раздела локального графа находятся рядом с полем; `aria-describedby` связывает сообщение с затронутыми полями, `aria-invalid` отмечает их.
