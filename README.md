# Переходы

Клиентский поиск цепочки гиперссылок между двумя статьями Википедии. React + TypeScript + Vite, двунаправленный BFS в Web Worker, запросы напрямую к MediaWiki Action API. Сервер не нужен.

Интерфейс устроен как детективная доска: статьи приколоты как улики, а красная нить соединяет центры карточек по их фактическим координатам на экране. Для поверхности доски, бумаги, булавок, скотча, нити и штампа сгенерированы изображения одного комплекта. Заголовки и метки набраны Unbounded, основной текст — Golos Text.

## Локальный запуск

```bash
npm ci
npm run dev
```

Откройте адрес Vite из терминала. Для проверки: `npm test` и `npm run build`.

Выберите один язык для пары и введите два названия статей или URL вида `https://ru.wikipedia.org/wiki/Москва`. Подсказки используют `list=search` выбранного раздела. URL автоматически переключает общий язык; две ссылки на разных языках требуют межъязыкового режима. Ссылки `?from=...&to=...&lang=...` заполняют форму; поиск запускается кнопкой, чтобы открытие ссылки не расходовало бюджет API. Кнопки позволяют поменять статьи местами и скопировать ссылку. Редиректы разрешаются перед поиском. Результат содержит ссылки на исходные статьи. Новый поиск и кнопка остановки завершают старый Web Worker.

Семь локальных изображений находятся в `src/assets/images/`; их исходные промпты и размеры перечислены в [каталоге ассетов](src/assets/images/README.md). Изображения участвуют в сборке Vite, внешних картинок на странице нет.

## Как работает поиск

`src/lib/linkSource.ts` задаёт три обязательные операции: `getOutlinks`, `getInlinks`, `resolveRedirect`. Обязательный интерфейс сохранён; пакетные операции, размеры и langlinks необязательны. BFS зависит только от LinkSource и SearchLimits. `ApiLinkSource` использует `prop=links|info` и `prop=linkshere|info` с `titles=A|B|C`, до 50 названий в группе. Все поля `continue` передаются следующему запросу того же батча, результаты страниц накапливаются без повторного старта отдельных статей. Пространство имён 0, входящие редиректы исключены. На всех API-запросах отправляется `Api-User-Agent`; транспорт ограничен шестью одновременными запросами, повторяет 429/5xx с экспоненциальной задержкой и учитывает Retry-After.

На каждом шаге расширяется меньший из текущих фронтов. Слой завершается целиком перед выбором следующей стороны: порядок статей внутри слоя не меняет длину пути. Поиск использует раунды 50, 200 и 500 ссылок на статью. Если раунд не дал пути, более широкий раунд пересобирает слои и родителей: новые рёбра могут изменить расстояния от старта. При этом кэш ссылок сохраняется. Размеры уже полученных страниц помогают порядку внутри слоя; дополнительных запросов размеров целого фронта нет. Ссылки кэшируются в памяти и IndexedDB на 30 дней; v2 базы отделяет новые linkshere от старого backlinks-кэша. При исчерпании бюджета воркер возвращает состояние, а «Искать дальше» продолжает текущий слой со свежим бюджетом. Прогресс показывает раунд, глубину и число посещённых статей.

Перед BFS адаптер может пройти до 30 первых ссылок в основном тексте от каждой из двух статей. Если из начальной статьи получается корректный направленный маршрут до цели, он сразу показывается как быстрый вариант, пока BFS ищет более короткий. Если цепочки сходятся в общей статье, обратная половина маршрута показывается только после проверки каждого обратного ребра: простое пересечение двух исходящих цепочек не доказывает существование пути к цели. Феномен первой ссылки описан [здесь](https://en.wikipedia.org/wiki/Wikipedia_philosophy_phenomenon).

Поиск ограничен. На каждой статье берутся первые N ссылок в порядке ответа API. Несуществующие статьи, встретившиеся среди ссылок, считаются тупиками и не прерывают поиск; для несуществующей начальной или конечной статьи остаётся ошибка. Жёсткий потолок в 500 ссылок сохраняется, поэтому даже результат BFS **может не быть глобально кратчайшим**. Первый найденный раунд завершает поиск. Поле `exact` отличает завершённый результат BFS от предварительного пути первой ссылки; оно не гарантирует глобальную оптимальность при обрезке API. На полном локальном графе рёбра не обрезаются. Отсутствие результата в пределах лимитов не доказывает отсутствие пути. `maxTotalRequests` ограничивает фактические HTTP-запросы в API-режиме, включая пагинацию и повторы; для простого мок-источника BFS считает вызовы `LinkSource`.

| Лимит | Значение |
| --- | ---: |
| `maxDepth` | 6 шагов с каждой стороны |
| `maxLinksPerPage` | 500 исходящих или входящих ссылок на статью |
| `widening` | 50 → 200 → 500 ссылок за три раунда |
| `maxTotalRequests` | 4000 HTTP-запросов на один запуск или продолжение |
| `concurrency` | 6 запросов API на приложение: до 5 в Worker + 1 для подсказок |
| `requestTimeout` | 10 секунд |
| `searchTimeout` | 90 секунд на один запуск или продолжение |
| `retryAttempts` | 2 повтора с экспоненциальной задержкой при 429/5xx |
| `fallbackChainMaxSteps` | 30 первых ссылок с каждой стороны |
| `fallbackTimeBudget` | 12 секунд на быстрые цепочки |

Изменяйте значения в `src/lib/searchLimits.ts`. API-адаптер ограничивает количество ссылок при получении; BFS дополнительно обрезает массив, чтобы тот же лимит соблюдался для источников, использующих этот лимит. Локальный Worker заменяет его на Number.MAX_SAFE_INTEGER и использует один полный раунд.

Для проверки граничных состояний в dev-сервере можно временно добавить к URL `?maxDepth=1&maxLinksPerPage=1` или `?maxTotalRequests=3`. В production эти параметры игнорируются; значения таблицы остаются неизменными.

## Подключение локального графа

Скачайте дампы одного снимка и одного языка с https://dumps.wikimedia.org/: `page` и `pagelinks`, для современного формата также `linktarget`, для разрешения редиректов — `redirect`. Сборщик читает SQL или SQL.gz построчно, использует схему CREATE TABLE и делает два прохода по pagelinks, заполняя исходящую и входящую CSR без списка объектов на каждое ребро.

```bash
npm run build:graph -- --lang ru --page ruwiki-page.sql.gz --pagelinks ruwiki-pagelinks.sql.gz --linktarget ruwiki-linktarget.sql.gz --redirect ruwiki-redirect.sql.gz
VITE_LINK_SOURCE=local npm run build
npm run preview
```

Результат — `public/graphs/ru.bin.gz`; `--out` позволяет изменить путь. Старый pagelinks с `pl_namespace` и `pl_title` не требует linktarget. Без redirect редиректы остаются обычными узлами; для полноценного графа добавляйте этот дамп. Исключаются пространства имён кроме 0, красные ссылки и межвики-редиректы. Формат WPFG v1: заголовок little-endian, JSON названий/алиасов, две пары uint32-массивов offsets/targets, затем gzip. Исходящие рёбра редиректов исключены, цели ссылок разрешаются до канонических статей.

Локальный адаптер загружает граф статическим запросом один раз на язык в каждом воркере. Подсказки API отключены. Воркер использует все рёбра без потолка 500; BFS возвращает кратчайший путь в графе в пределах глубины и времени. Поиск не обращается к Wikipedia. Открытие карточки вручную ведёт на Wikipedia. Большие графы требуют памяти для названий, обоих CSR и распакованного файла; полный ruwiki/enwiki может не поместиться в мобильный браузер. Графы не входят в git и должны быть собраны до деплоя.

## Межъязыковой режим

В API-режиме включите «Межъязыковой поиск (langlinks)» и выберите язык цели либо вставьте две Wikipedia-ссылки. Режим работает в разделах начальной и конечной статьи. Рёбра langlinks направленные: обратного индекса у Action API нет, поэтому адаптер использует прямой BFS и не выдумывает обратные переводы. Это медленнее двунаправленного поиска и ограничено шестью шагами от старта. Межъязыковой переход считается одним шагом; это переход языка, а не обязательно ссылка в тексте статьи. Локальный CSR пока одноязыковой.

## Проверки и PWA

```bash
npm test                     # включая 200 случайных графов, все пары и перебор
npm run build
npx playwright install chromium
npm run test:e2e             # замоканный Action API, axe, 360px, PWA офлайн
npm run test:local           # сборка тестового CSR, local build и реальный Worker
npm run test:lighthouse      # 3 mobile запуска; медиана каждой категории >= 90
```

`test:local` создаёт тестовый `public/graphs/en.bin.gz` (шесть статей, это не дамп английской Wikipedia) и `dist-local/`. Удалите этот файл перед production-сборкой или замените полноценным графом. В CI тестовый файл удаляется автоматически. `npm run test:lighthouse` запускает preview при необходимости, использует установленный Playwright Chromium и сохраняет HTML/JSON в `lighthouse-reports/`; адрес можно переопределить `LIGHTHOUSE_URL`. `LIGHTHOUSE_URL` должен указывать на production-сборку. Проверки Playwright используют production preview и блокируют Service Worker в сценариях API, проверяя PWA отдельно. Артефакты: `playwright-report/`, `test-results/`.

CI (`.github/workflows/ci.yml`) проверяет pull requests и main: unit/property, сборку, E2E с axe, mobile Lighthouse и local Worker. Deploy workflow выполняет те же проверки перед публикацией и отдельно пересобирает приложение с GitHub Pages base. Для проверки по корню localhost поддерживается `VITE_BASE_PATH=/`.

Сборка генерирует manifest и версионный service worker: оболочка, картинки и локальные шрифты доступны офлайн после первой загрузки. Wikipedia API офлайн недоступен; precache не сохраняет его ответы. IndexedDB-кэш ссылок остаётся отдельным. Графы не precache-ятся автоматически, чтобы установка PWA не скачивала гигабайты. В новом поиске новый Worker загружает локальный граф снова. Для установки PWA используйте HTTPS или localhost; браузерная поддержка установки по SVG-иконке зависит от платформы.

Dev-зависимости: Playwright — браузерные сценарии; `@axe-core/playwright` — доступность; Lighthouse — mobile аудит; `tsx` — выполнение типизированного сборщика. Новых runtime-зависимостей нет. Unbounded и Golos Text размещены локально с лицензиями SIL OFL в `src/assets/fonts/`.

Подробный отчёт по этапам и ограничениям: [IMPLEMENTATION_REPORT.md](IMPLEMENTATION_REPORT.md).

## Деплой форка на GitHub Pages

1. Загрузите проект в репозиторий GitHub с веткой `main`.
2. В **Settings → Pages → Build and deployment** выберите **GitHub Actions**.
3. Push в `main` запускает тесты, сборку и публикацию `dist` через `.github/workflows/deploy.yml`.

При сборке в GitHub Actions `vite.config.ts` берёт имя репозитория из `GITHUB_REPOSITORY` и выставляет `base=/<repo>/`. Для ссылки в футере можно задать `VITE_GITHUB_URL` в окружении сборки; иначе используется адрес исходного проекта.
