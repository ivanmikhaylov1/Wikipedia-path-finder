# Переходы

Клиентский поиск цепочки гиперссылок между двумя статьями Википедии. React + TypeScript + Vite, двунаправленный BFS в Web Worker, запросы напрямую к MediaWiki Action API. Сервер не нужен.

Интерфейс устроен как детективная доска: статьи приколоты как улики, а красная нить соединяет центры карточек по их фактическим координатам на экране. Для поверхности доски, бумаги, булавок, скотча, нити и штампа сгенерированы изображения одного комплекта. Заголовки и метки набраны PT Mono, основной текст — Golos Text.

## Локальный запуск

```bash
npm ci
npm run dev
```

Откройте адрес Vite из терминала. Для проверки: `npm test` и `npm run build`.

Выберите один язык для пары и введите два названия статей или URL вида `https://ru.wikipedia.org/wiki/Москва`. Подсказки используют `list=search` выбранного раздела. URL автоматически переключает общий язык; две ссылки на разных языках отклоняются до старта поиска. Редиректы разрешаются перед поиском. Результат содержит ссылки на исходные статьи. Новый поиск и кнопка остановки завершают старый Web Worker.

Семь локальных изображений находятся в `src/assets/images/`; их исходные промпты и размеры перечислены в [каталоге ассетов](src/assets/images/README.md). Изображения участвуют в сборке Vite, внешних картинок на странице нет.

## Как работает поиск

`src/lib/linkSource.ts` задаёт три обязательные операции: `getOutlinks`, `getInlinks`, `resolveRedirect`. Дополнительные методы позволяют получать исходящие ссылки пачками, размеры страниц и первую ссылку в основном тексте. `ApiLinkSource` запрашивает `prop=links|info` для группы до 50 статей; размер страницы приходит в том же ответе. MediaWiki пагинирует общую выдачу, поэтому после первого батча адаптер дозапрашивает неполные страницы. `list=backlinks` поддерживает только один `bltitle` на запрос. Адаптер использует пространство имён 0, `origin=*`, лимит параллелизма и повторы при 429/5xx.

Поиск идёт раундами с лимитом 50, 200 и 500 ссылок на статью. В следующем раунде BFS сохраняет посещённые узлы и родителей, расширяя те же фронты с большим лимитом. Размеры страниц помогают раньше проверять менее крупные узлы. Ссылки кэшируются в памяти и в IndexedDB на 30 дней; ключи имеют вид `ru:Название:out` и `ru:Название:in`. При исчерпании бюджета воркер возвращает состояние поиска, а кнопка «Искать дальше» запускает продолжение со свежим бюджетом. Прогресс показывает раунд, глубину и число посещённых статей.

Перед BFS адаптер может пройти до 30 первых ссылок в основном тексте от каждой из двух статей. Если из начальной статьи получается корректный направленный маршрут до цели, он сразу показывается как быстрый вариант, пока BFS ищет более короткий. Если цепочки сходятся в общей статье, обратная половина маршрута показывается только после проверки каждого обратного ребра: простое пересечение двух исходящих цепочек не доказывает существование пути к цели. Феномен первой ссылки описан [здесь](https://en.wikipedia.org/wiki/Wikipedia_philosophy_phenomenon).

Поиск ограничен. На каждой статье берутся первые N ссылок в порядке ответа API. Несуществующие статьи, встретившиеся среди ссылок, считаются тупиками и не прерывают поиск; для несуществующей начальной или конечной статьи остаётся ошибка. Жёсткий потолок в 500 ссылок сохраняется, поэтому даже результат BFS **может не быть глобально кратчайшим**. Отсутствие результата в пределах лимитов не доказывает отсутствие пути. `maxTotalRequests` ограничивает фактические HTTP-запросы в API-режиме, включая пагинацию и повторы; для простого мок-источника BFS считает вызовы `LinkSource`.

| Лимит | Значение |
| --- | ---: |
| `maxDepth` | 6 шагов с каждой стороны |
| `maxLinksPerPage` | 500 исходящих или входящих ссылок на статью |
| `widening` | 50 → 200 → 500 ссылок за три раунда |
| `maxTotalRequests` | 4000 HTTP-запросов на один запуск или продолжение |
| `concurrency` | 6 запросов API одновременно |
| `requestTimeout` | 10 секунд |
| `searchTimeout` | 90 секунд на один запуск или продолжение |
| `retryAttempts` | 2 повтора с экспоненциальной задержкой при 429/5xx |
| `fallbackChainMaxSteps` | 30 первых ссылок с каждой стороны |
| `fallbackTimeBudget` | 12 секунд на быстрые цепочки |

Изменяйте значения в `src/lib/searchLimits.ts`. API-адаптер ограничивает количество ссылок при получении; BFS дополнительно обрезает массив, чтобы тот же лимит соблюдался и для будущего локального источника.

Для проверки граничных состояний в dev-сервере можно временно добавить к URL `?maxDepth=1&maxLinksPerPage=1` или `?maxTotalRequests=3`. В production эти параметры игнорируются; значения таблицы остаются неизменными.

## Подключение локального графа

Скачайте дампы одного снимка и одного языка с https://dumps.wikimedia.org/: `page` и `pagelinks`, для современного формата также `linktarget`, для разрешения редиректов — `redirect`. Сборщик читает SQL или SQL.gz построчно, использует схему CREATE TABLE и делает два прохода по pagelinks, заполняя исходящую и входящую CSR без списка объектов на каждое ребро.

```bash
npm run build:graph -- --lang ru --page ruwiki-page.sql.gz --pagelinks ruwiki-pagelinks.sql.gz --linktarget ruwiki-linktarget.sql.gz --redirect ruwiki-redirect.sql.gz
VITE_LINK_SOURCE=local npm run build
npm run preview
```

Результат — `public/graphs/ru.bin.gz`; `--out` позволяет изменить путь. Старый pagelinks с `pl_namespace` и `pl_title` не требует linktarget. Без redirect редиректы остаются обычными узлами; для полноценного графа добавляйте этот дамп. Исключаются пространства имён кроме 0, красные ссылки и межвики-редиректы. Формат WPFG v1: заголовок little-endian, JSON названий/алиасов, две пары uint32-массивов offsets/targets, затем gzip. Исходящие рёбра редиректов исключены, цели ссылок разрешаются до канонических статей.

Локальный адаптер загружает граф статическим запросом один раз на язык в каждом воркере. Подсказки API отключены. Воркер использует все рёбра без потолка 500; BFS возвращает кратчайший путь в графе в пределах глубины и времени. Поиск не обращается к Wikipedia. Открытие карточки вручную ведёт на Wikipedia. Большие графы требуют памяти для названий, обоих CSR и распакованного файла; полный ruwiki/enwiki может не поместиться в мобильный браузер. Графы не входят в git и должны быть собраны до деплоя.

## Межъязыковой режим

В API-режиме включите «Межъязыковой поиск (langlinks)» и выберите язык цели либо вставьте две Wikipedia-ссылки. Режим работает в разделах начальной и конечной статьи. Рёбра langlinks направленные: обратного индекса у Action API нет, поэтому адаптер использует прямой BFS и не выдумывает обратные переводы. Это медленнее двунаправленного поиска и ограничено шестью шагами от старта. Межъязыковой переход считается одним шагом; это переход языка, а не обязательно ссылка в тексте статьи. Локальный CSR пока одноязыковой.

## Возможные улучшения

Позже можно добавить scheduled GitHub Actions workflow, который собирает и обновляет список статей-хабов для порядка расширения. В этой версии размеры страниц берутся из API; workflow и отдельный датасет хабов не добавлены.

## Деплой форка на GitHub Pages

1. Загрузите проект в репозиторий GitHub с веткой `main`.
2. В **Settings → Pages → Build and deployment** выберите **GitHub Actions**.
3. Push в `main` запускает тесты, сборку и публикацию `dist` через `.github/workflows/deploy.yml`.

При сборке в GitHub Actions `vite.config.ts` берёт имя репозитория из `GITHUB_REPOSITORY` и выставляет `base=/<repo>/`. Для ссылки в футере можно задать `VITE_GITHUB_URL` в окружении сборки; иначе используется адрес исходного проекта.
